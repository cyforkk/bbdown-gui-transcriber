# Git 提交规范

中文 commit message + 合理拆分。目标：让历史可读、可回溯、可 cherry-pick。

## commit message 格式

```
<类型>: <简短描述>

<可选正文，多行说明动机/影响/注意事项>
```

- 第一行：类型 + 冒号 + 空格 + 描述，不超过 50 字。
- 正文空一行后写，每行不超过 72 字，说明"为什么改、改了什么影响、踩了什么坑"。
- 不要写"修改若干文件""更新代码"这类无信息描述。

## 类型清单

| 类型 | 用于 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档改动 |
| `refactor` | 重构，行为不变 |
| `perf` | 性能优化 |
| `test` | 增补或修正测试 |
| `chore` | 构建、依赖、配置、版本号等杂项 |
| `ci` | CI/CD 配置改动 |
| `style` | 格式调整，不影响逻辑 |
| `revert` | 回滚某次提交 |

## 拆分粒度

- 一个 commit 只解决一件事：要么修一个 bug，要么加一个功能，要么改文档。
- 一个功能涉及多文件（代码 + 测试 + 文档）可放一个 commit，因为它们属于同一逻辑改动。
- 不要为了"提交干净"把修 bug 和顺手重构混在一起——拆成 `fix:` 和 `refactor:` 两个。
- 大功能分阶段提交：每阶段可独立验证，便于 review 和回滚。

## 示例

好：

```
feat: 视频选择弹窗支持 Shift 范围选与 Ctrl 追加切换

Listbox 由 MULTIPLE 改为 EXTENDED，多选语义同 Windows 资源管理器：
单击替换、Ctrl+单击追加切换、Shift+单击连续范围选。
功能文档同步更新多选语义说明。
```

差（不要这样）：

```
更新了代码
修改弹窗和一些文档，还顺手调了打包脚本
```

## 不要提交的内容

- 构建产物：`dist/`、`build/`、`release/`、`*.exe`、`*.zip`、`*.spec`。
- 临时文件：`*.log`、缓存、IDE 目录（`.idea/`、`.vscode/` 视团队约定）。
- 大文件：二进制、模型、视频、图片素材等，走 Git LFS 或外部存储。
- 本地配置：数据库连接串、密钥、`.env`、本地 AI 会话状态（如 `.codebuddy/`）。

依赖 `.gitignore` 排除，提交前 `git status` 复核不应出现这些。

## 一个实用判断

- 提交信息能不能让人不看 diff 就知道改了什么？不能 → 重写。
- 这次改动能不能用一句话概括？不能 → 拆成多个 commit。
- `git status` 里有不该入库的文件？→ 加进 `.gitignore`，别 `git add -A` 一把梭。
