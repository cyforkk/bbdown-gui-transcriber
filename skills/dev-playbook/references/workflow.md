# 开发工作流

修 bug 和加功能是两条线，但都走"复现 → 定位 → 改 → 验证 → 文档 → 自检"六阶段。区别只在每阶段的具体动作。

## 先判断属于哪条线

| 线索 | 属于 | 起手 |
| --- | --- | --- |
| 现象是"原本正常现在坏了"/"报错"/"行为不符合预期" | 修 bug | 先复现，再定位根因 |
| 现象是"想要一个新能力"/"现在没有这个功能" | 加功能 | 先确认需求边界，再设计方案 |
| 拿不准 | 按修 bug 处理 | 先复现，复现过程会暴露是 bug 还是缺功能 |

## 修 bug 线

### 1. 复现

- 先要一个**可稳定复现**的最小路径。"偶尔出现"先想办法变成"必然出现"。
- 复现不了就别动手改，盲改大概率引入新问题。
- 复现路径要能写进 issue 或 commit message，让别人也能照着走一遍。

### 2. 定位根因

- 顺着报错栈/日志追到具体文件和行，**不要靠猜**。
- 改之前先读相关代码，搞清调用链和上下游。
- 区分"根因"和"表象"：报错的位置不一定是该改的位置。
- 多个原因叠加时，逐个验证，别一次改多处。

### 3. 改代码

- 只改根因相关的代码，不顺手重构无关部分。
- 改动尽量小而集中，方便 review 和回滚。
- 改完先在本地跑通复现路径，确认现象消失。

### 4. 验证

- 跑现有测试套件，确认没引入回归。
- 补一个针对本次 bug 的回归测试，锁定修复。
- 涉及运行进程的，确认跑的是新代码（重启进程/重打包）。

### 5. 文档

- 把"现象/根因/修复/经验教训"写进项目问题文档或 `gotchas.md`。
- 改了对外行为的，同步更新对应功能文档。

### 6. 自检

- 过一遍 `checklist.md`。
- 交付前确认：代码改了、测试过了、文档更新了、没顺手改无关代码。

## 加功能线

### 1. 确认需求

- 搞清"给谁用、解决什么、怎么算成功"。
- 需求模糊时先 brainstorm，不要直接写代码。
- 确认是否有现成实现可以复用，避免重复造轮子。

### 2. 设计方案

- 列出入口文件、改动范围、与现有模块的协作方式。
- 大功能先拆步骤，每步可独立验证。
- 接口/数据结构先定，再写实现。

### 3. 改代码

- 按设计逐步实现，每步跑通再下一步。
- 新增公开接口的，顺手补文档。
- 不为"以后可能用到"提前加抽象，等第二个用例出现再抽。

### 4. 验证

- 每个新功能至少一个测试覆盖主路径。
- 跑全量测试确认无回归。
- 实际操作一遍功能，确认用户视角可用。

### 5. 文档

- 更新功能文档，说明新能力、用法、边界。
- 踩到的坑写进 `gotchas.md` 或项目问题文档。

### 6. 自检

- 过一遍 `checklist.md`。

## 一个实用判断

- 改了代码但现象没变 → 八成没跑新代码，或改的不是根因位置。先确认进程/产物是新的，再回看定位。
- 改了代码出新报错 → 大概率是改动引入的回归，先回滚到能跑的版本再缩小改动。
- 同一个问题反复修不好 → 回到第 1 步重新复现，前几次很可能修的是表象。
