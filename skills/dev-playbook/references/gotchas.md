# 通用易错点

跨项目通用的开发踩坑，按现象组织。每条都给"第一检查点"和"常见原因"。

## 最常见误区

- 改了代码就以为生效，没确认运行的是新进程/新产物。
- 用"起子进程跑命令"做可用性探测，被超时/拦截/启动慢误判。
- 错误信息把多种可能混排成一句话，用户无法定位。
- 间歇性失败先怀疑本地配置，不怀疑服务端风控/限流。
- 给第三方 API 调用不加重试退避。
- 销毁 UI 控件后还访问其方法/属性。
- 滚动列表用"Canvas 嵌普通控件"的 hack，跨环境渲染不一致。
- 自动生成的索引/产物手改后下次重跑被覆盖。

## 现象到检查点

| 现象 | 第一检查点 | 常见原因 |
| --- | --- | --- |
| 改了代码但行为没变 | 确认跑的是新进程/新打包产物 | 旧进程未杀、缓存未清、跑的是别的版本 |
| 自动检测/探测时好时坏 | 把探测方式从"跑子进程"改成"查文件系统" | 子进程被超时/杀软/启动慢误判为不可用 |
| 偶尔失败、稍后自愈 | 怀疑服务端风控/限流，加重试退避 | 服务端间歇性拦截裸请求 |
| 接口返回 HTML 不是 JSON | 检查 Content-Type 和是否带鉴权 | 风控拦截页 / 缺登录态 / UA 异常 |
| 错误信息笼统说"网络问题" | 看真实响应码和响应体 | 可能是 412/403/非 JSON，不是网络层 |
| UI 控件销毁后报"invalid command name" | 在 destroy 前把数据取出 | wait_window 返回后控件已死 |
| 滚动列表/嵌套 Frame 不显示 | 改用原生滚动控件 | Canvas+create_window 跨环境渲染不一致 |
| 分页拉取数量不全 | 看是否以"短页"作终止条件 | 短页不代表拉完，应按总数目标+去重 |
| 大列表/大文件处理卡顿 | 确认是真瓶颈还是没进度反馈 | 多数是没给进度日志，让用户以为卡死 |
| 第三方 API 偶尔 429/412 | 加可重试特征识别+指数退避 | 限流/风控，重试几次就过 |

## 一个实用判断

- "改了没反应"→ 先确认跑的是新代码，再看改的位置对不对。
- "时好时坏"→ 先怀疑服务端间歇性拦截，别先怀疑本地配置。
- "笼统错误"→ 去看真实响应/日志原文，别被错误信息文字带偏。
- "拉取不全"→ 检查终止条件是否依赖了不可靠的信号（如短页）。
