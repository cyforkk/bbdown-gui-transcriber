# dev-playbook

把"修一个 bug / 加一个功能"从模糊需求走到验收闭环的标准动作序列。只管"按什么顺序做什么、每步守什么"，不绑定任何语言、框架或业务域。

## 使用顺序

- 先看 `references/workflow.md`，确认这次属于"修 bug"还是"加功能"，以及当前该停在哪个阶段。
- 再看 `references/gotchas.md`，对照本次最容易踩的坑（改了没生效、间歇性失败、错误信息误导等）。
- 收尾时看 `references/checklist.md`，逐条自检再交付。

## 必守约束

- 每次改动只解决一类问题，不要顺手改无关代码。
- 改完代码必须跑测试或实际验证通过再交付，不交"应该能跑"的代码。
- 改了运行中的进程（GUI、守护进程、长驻服务）相关代码后，必须确认跑的是新进程，排查"改了没反应"先怀疑旧进程。
- 错误信息要按真实原因分级提示，不要把"网络/权限/登录/不存在"混排成一句话。
- 文档与代码同步更新：本次改了什么行为，对应文档同步；踩过的坑沉淀进 `gotchas.md` 或项目问题文档。
