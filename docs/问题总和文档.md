# 问题总和文档

## BBDown 不内置的分发问题

### 问题说明

将 BBDown 直接打进 exe 会带来许可证、体积、更新和调试复杂度问题。

### 处理方式

采用方案 B：不内置 BBDown，但支持同目录 `bbdown.exe` 自动检测。

### 检测顺序

1. 当前工作目录下的 `bbdown.exe` / `BBDown.exe`（文件名忽略大小写）。
2. 用户目录 `.dotnet/tools`（如 `C:\Users\<用户名>\.dotnet\tools\BBDown.exe`，忽略大小写）。
3. exe 同目录 `bbdown.exe`（源码运行时为项目根目录）。
4. 系统 PATH 中的 `bbdown`。
5. 用户手动选择。

## Faster-Whisper 打包体积问题

### 问题说明

接入 Faster-Whisper 后，PyInstaller 打包体积从早期约 8.67 MB 增长到约 91.58 MB。

### 当前策略

接受该体积作为包含转文字依赖的 GUI 发布版，同时仍不内置 BBDown。

## 视频转文字能力边界

### 问题说明

视频转文字识别的是视频文件中的音频流，不识别画面文字，不做 OCR。无音频流或损坏视频会被记录为失败。

## 批量转文字失败处理

### 修复方式

转录前使用 `ffprobe` 校验媒体文件，单个文件损坏或识别为空不会中断整个批量任务。


## .NET global tool 版 BBDown 复制到 release 后不可用

### 问题现象

将 .NET 全局工具安装目录中的 `bbdown.exe` 复制到 `release` 后，GUI 优先使用该文件，但下载时报：

```text
The application to execute does not exist
```

### 原因

.NET global tool 的 `bbdown.exe` 不一定是完整便携版程序，复制到其他目录后可能找不到实际应用。

### 修复方式

GUI 自动检测链路已直接包含用户目录 `.dotnet/tools` 原始路径（在应用目录、PATH 之前），因此无需复制该 `bbdown.exe` 到 release。同目录检测到不可用的文件时自动跳过并继续回退。

### 使用建议

方案一：继续使用原始 .NET 全局工具路径，不要复制该 `bbdown.exe` 到 release。

方案 B 只适合官方便携版或可独立运行的 `bbdown.exe`。


## 转文字任务 transcriber 局部变量遮蔽问题

### 问题现象

GUI 点击开始转文字后立即失败：

```text
转文字任务失败：cannot access local variable 'transcriber' where it is not associated with a value
```

### 原因

`run_transcription` 中使用局部变量名 `transcriber` 接收 `AudioTranscriber` 实例，遮蔽了导入的 `transcriber` 模块，导致 Python 在函数作用域内无法访问模块引用。

### 修复方式

将局部变量改名为 `audio_model`，保持 `transcriber` 始终指向模块；新增回归测试覆盖文件夹转文字路径。


## exe 中 Faster-Whisper VAD 模型文件缺失问题

### 问题现象

release exe 转文字时报错：

```text
faster_whisper/assets/silero_vad_v6.onnx failed. File doesn't exist
```

### 原因

`model.transcribe(..., vad_filter=True)` 需要 Faster-Whisper 包内的 `assets/silero_vad_v6.onnx`，PyInstaller 未默认收集该数据文件。

### 修复方式

打包命令增加：

```text
--collect-data faster_whisper
```

新版 release exe 已重新打包，体积约 92.61 MB。

## ffprobe 校验媒体文件时弹出黑色 CMD 窗口

### 问题现象

转文字前校验媒体文件时会短暂弹出黑色 CMD 窗口。

### 原因

`probe_media_file()` 调用 `ffprobe` 时未传入 Windows 隐藏子进程窗口参数。

### 修复方式

为 `ffprobe` 子进程添加 `STARTUPINFO`、`STARTF_USESHOWWINDOW` 和 `SW_HIDE`，保持输出重定向但不显示窗口。


## release exe 转文字时 CUDA cublas DLL 缺失问题

### 问题现象

选择文件夹批量转文字时，模型加载后单个文件转写失败：

```text
Library cublas64_12.dll is not found or cannot be loaded
```

### 原因

Faster-Whisper 使用 CUDA 时依赖 `nvidia-cublas-cu12` 和 `nvidia-cudnn-cu12` 包内的 DLL。源码环境可以从 `.venv` 找到这些 DLL，但 PyInstaller 单文件 exe 未自动收集 CUDA 二进制文件，并且运行时没有把 `_MEIPASS` 临时解包目录加入 DLL 搜索路径。

### 修复方式

打包命令增加：

```text
--collect-binaries nvidia.cublas
--collect-binaries nvidia.cudnn
```

运行时优先把 PyInstaller `_MEIPASS` 临时目录加入 CUDA DLL 搜索范围，再调用 `os.add_dll_directory()` 和补充 `PATH`。


## 单文件 release exe 启动过慢问题

### 问题现象

双击 `BilibiliDownloaderUI.exe` 启动很慢。

### 原因

单文件 PyInstaller exe 包含 CUDA、cuBLAS、cuDNN、Faster-Whisper 等大依赖，体积超过 1GB。`--onefile` 每次启动都要先解压内部文件到临时目录，导致启动耗时明显。

### 修复方式

打包方式改为 PyInstaller `--onedir` 文件夹版发布，生成 `release/BilibiliDownloaderUI/BilibiliDownloaderUI.exe`。大依赖保留在 `_internal` 等目录中，启动时不再重复解压整个大包。


## release 大文件进入 Git 历史导致 push 失败问题

### 问题现象

将包含 CUDA/Faster-Whisper 依赖的 `release/` 发布成品提交到 git 后，推送 GitHub 失败或连接被重置。

### 原因

文件夹版发布包包含大量 DLL 和依赖文件，仓库对象一度达到 GiB 级别。GitHub 普通源码仓库不适合直接存放这类发布成品。

### 修复方式

从 git 历史中移除 `release/`，并在 `.gitignore` 中忽略发布成品。源码仓库只保存代码、测试、文档和构建脚本；发布成品压缩为 zip 后通过 GitHub Releases 分发。


## 文件夹版 release 缺少 Tcl/Tk 数据导致启动失败

### 问题现象

双击文件夹版 `BilibiliDownloaderUI.exe` 启动失败：

```text
FileNotFoundError: Tcl data directory "...\_internal\_tcl_data" not found
```

### 原因

文件夹版发布目录不完整，缺少 Tkinter 运行时需要的 `_tcl_data` 和 `_tk_data` 目录。该问题通常来自只复制 exe、发布目录残缺，或打包后未校验必要运行数据。

### 修复方式

构建脚本增加发布目录校验：打包完成后必须存在 `BilibiliDownloaderUI.exe`、`_internal/_tcl_data` 和 `_internal/_tk_data`，否则构建失败。本地 release 已从完整备份恢复，确保 Tkinter 运行数据存在。


## BBDown 返回成功但下载目录为空的假成功问题

### 问题现象

GUI 日志显示下载成功，但用户选择的下载目录为空。

### 原因

旧逻辑只根据 BBDown 进程退出码判断成功。若 BBDown 返回 `0` 但没有在目标目录生成媒体文件，GUI 仍会显示下载成功，导致“假成功”。

### 修复方式

下载前记录目标目录已有的音频/视频/字幕文件，下载后扫描新增文件。只有检测到新增下载产物时才记为成功，并在日志里输出实际文件路径；如果 BBDown 返回 `0` 但没有新增文件，则记录失败：`BBDown 执行完成，但未检测到下载文件`。


## GitHub Release 发布包超过 1GB 导致上传不稳定问题

### 问题现象

文件夹版发布包压缩后仍超过 1GB，上传 GitHub Release 时容易失败或中断。

### 原因

转文字功能依赖 Faster-Whisper、CUDA、cuBLAS、cuDNN、onnxruntime、numpy 和 Python 运行环境，完整 Windows 发布包体积很大。

### 处理方式

项目改为源码运行优先：GitHub 仓库只提供源码、文档、测试和打包脚本，不再推荐上传大体积 Release 包。用户通过 `uv sync` 安装依赖后运行 `uv run bbdown-gui`；需要 exe 的用户可在本机自行打包。


## 只下载用户不需要安装转文字大依赖

### 问题现象

部分用户只需要下载视频/音频，不需要转文字，但旧依赖默认安装 Faster-Whisper、CUDA、cuBLAS、cuDNN 等大依赖，安装慢且占用空间大。

### 原因

转文字依赖被放在默认 dependencies 中，导致所有用户都会安装。

### 修复方式

将转文字依赖移动到 `transcribe` optional extra。默认 `uv sync` 只安装轻量下载模式；需要转文字的用户执行 `uv sync --extra transcribe`。GUI 在缺少转文字依赖时给出明确提示，不影响下载功能。


## 下载生成全 0 或损坏视频仍被判定成功

### 问题现象

GUI 显示下载成功，但部分后续下载的 `.mp4` 无法播放。检查文件内容时发现开头大量为：

```text
00 00 00 00 00 00 00 00 ...
```

### 原因

上一版只检查 BBDown 返回成功后是否有新增文件。若 BBDown 生成了全 0、过小、未完整写入的媒体文件，或者只生成字幕文件，仍可能被判定为下载成功。

### 修复方式

下载完成后不仅检查新增文件，还会筛选有效主媒体文件：

- 字幕文件 `.srt` / `.ass` 不作为下载成功依据。
- 文件大小必须超过最小阈值。
- 文件头不能全是 `0x00`。

如果 BBDown 返回成功但没有有效媒体文件，会记录失败：`BBDown 执行完成，但未检测到有效下载文件`。


## GitHub Actions Windows runner 中文输出 UnicodeEncodeError

### 问题现象

打 tag 触发 `Release` 工作流后，`Build (lite edition)` 步骤立即失败：

```text
UnicodeEncodeError: 'charmap' codec can't encode characters in position 0-6: character maps to <undefined>
```

失败位置在 `scripts/build_exe.py` 的 `print('执行打包命令：')`。

### 原因

GitHub Actions `windows-latest` runner 的 PowerShell 控制台默认使用 cp1252 编码，Python 的 stdout 随之用 cp1252 编码，无法输出中文字符。本地 Windows 开发机控制台一般是 UTF-8 或 GBK，不会暴露该问题，所以只在 CI 上触发。

### 修复方式

在 `.github/workflows/release.yml` 的 job 级别设置环境变量：

```yaml
env:
  PYTHONUTF8: '1'
```

启用 Python UTF-8 模式，强制 stdin/stdout/stderr 使用 UTF-8。不改动源码，本地行为不变。


## 视频合集下载报「获取视频合集失败」

### 问题现象

GUI 选择「视频合集」来源，粘贴合集链接（如 `https://space.bilibili.com/<mid>/lists/<id>?type=season`）后下载，日志报：

```text
任务失败：获取视频合集失败：可能是合集不存在、合集为私有，或网络无法访问哔哩哔哩。
```

### 原因

两个叠加原因：

1. **接口用错**：旧代码调用 `x/space/series/archives`（「系列 series」接口，参数 `series_id`），而 `type=season` 的合集需要 `x/polymer/web-space/seasons_archives_list`（参数 `season_id`、`page_num`、`page_size`）。系列接口对合集 id 直接返回错误。
2. **风控拦截**：合集接口裸请求（无 WBI 签名）会被 B 站风控拒绝，返回 `code: -352` 或 HTML 错误页。

### 修复方式

`downloader.py` 重写合集列表拉取逻辑：

- 换用正确接口 `x/polymer/web-space/seasons_archives_list`。
- 实现 WBI 签名（纯标准库）：从免登录的 `x/web-interface/nav` 取 `img_key`/`sub_key`，按官方混淆表生成 mixin key（进程内缓存），对参数追加 `wts` 时间戳并计算 `w_rid` MD5 签名。
- 三级自动回退：WBI 签名请求 → 未签名请求 → 旧接口 `x/polymer/space/seasons_archives_list`。第一页成功后记住可用通道，后续分页直接复用。

### 验证结论

2026-09-01 实测：签名请求对合集 `season_id=7132285` 返回 `code: 0`，共 54 个视频（分页 30 + 24），签名算法与 B 站线上一致。


## BBDown 自动检测漏掉用户目录且 `--version` 校验误判

### 问题现象

机器上已通过 `dotnet tool install` 安装 BBDown（位于 `C:\Users\<用户名>\.dotnet\tools\BBDown.exe`），但 GUI 点「检测 BBDown」始终弹「未在 PATH 中检测到 bbdown」。

### 原因

三个叠加缺陷：

1. 模块级 `detect_bbdown_executable()` 只查应用目录和 PATH，不查用户 `.dotnet/tools`。
2. GUI 按钮 `detect_bbdown()` 只调 `shutil.which('bbdown')`，没有复用模块级完整检测函数，两处逻辑分叉。
3. `is_bbdown_usable()` 通过执行 `bbdown --version` 子进程校验，某些环境下（如 .NET global tool 的 shim 启动慢、被杀软拦截、超时）返回非 0 或抛异常，导致真实存在的 BBDown 被误判为不可用，检测链路一路跳过。

### 修复方式

- 检测优先级重排：当前工作目录（`iterdir()` 扫描，文件名忽略大小写，命中 `bbdown.exe`/`BBDown.exe`/`bbdown`）→ 用户目录 `.dotnet/tools`（同样大小写无关扫描）→ 应用目录 `bbdown.exe` → PATH。
- `detect_bbdown()` 改为复用 `detect_bbdown_executable()`，消除两处逻辑分叉。
- `is_bbdown_usable()` 不再执行子进程，只检查文件存在性（Windows 检查 `.exe` 后缀，其他平台检查可执行位）。真正不可用的文件在下载阶段由 BBDown 自身的报错暴露。

### 经验教训

- 检测类功能要保持单一入口，GUI 按钮和初始化共用同一函数，否则极易出现「一处修了另一处还是旧行为」。
- 用「执行子进程校验版本」做可用性探测不可靠，超时/拦截/启动慢都会误判；能用文件系统判断就不要起子进程。
- 修改代码后必须重启 GUI 进程才生效，排查「改了没反应」时先确认跑的不是旧进程。
